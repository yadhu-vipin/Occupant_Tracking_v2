## 1. Quick start

Python 3.12. From the repo root:

```bash
python -m pip install -r requirements.txt
python manage.py test        # whole test suite (234 tests, a few seconds)
python manage.py pipeline    # roles -> enroll -> events -> Phase 2 -> 3 -> 4  (seed 42)
python manage.py states      # per-state TP/FP/TN/FN against ground truth, averaged over all states
```

## 2. What the project is

A research prototype of **decentralised occupant identification and tracking across campus buildings**. There are 10 buildings with 50 registered occupants each (500 people). Each building keeps its own face embeddings and its own state. No central server holds everyone's biometrics.

The problem: a camera in building A sees a face. If it is one of A's 50 people, A recognises it locally. If not, it may be a visitor registered elsewhere. A should find the right building without asking all nine and without anyone sharing galleries.

The answer is a cascade:

1. **Local check.** Compare the capture with A's own registered references (vote rule: at least 12 of 20 reference vectors within 80.43°).
2. **Visitor pool.** If the person was already identified as a visitor in A, match against the cached references.
3. **Routing.** If still unknown, hash the capture with LSH and test the hashes against the nine peers' published Bloom filters. This yields a ranked shortlist of the most likely buildings (default 5, with 3 weak-bit probes).
4. **Remote verification.** Ask shortlisted buildings in rank order. A candidate runs the same vote on its own gallery and, on a match, returns the person's reference vectors. The reply is sealed (encrypted and signed).
5. **State.** The identification becomes a probability distribution over zones (Definition 3.3 + BSTS) stored in the building that saw the person. A small *visit pointer* is sent to the person's home building so location queries can be redirected.
6. **Queries.** Spatio-temporal questions (Q1–Q13, TRACK) are answered over that state, gated by two layers of role-based access control.

Key idea: the Bloom filter is a **one-way routing index**. It tells you which building *probably* has a match; only the building's own vote decides identity. Bloom hits can be false positives, which is why verification is always needed.

What is real and what is simulated: embeddings come from a stored corpus, not a camera. Inter-building calls are in-process Python calls (sealed as if they crossed a network). Nothing in this repository is deployed across machines.

```

                                                                                   mints visit pointers)

```

Run order (`python manage.py pipeline` does all of it):

```bash
python build_campus_roles.py
python pipeline/enroll_and_broadcast.py --all
python pipeline/generate_events.py --seed 42
python pipeline/route_and_recognize.py --phase 2
python pipeline/route_and_recognize.py --phase 3
python pipeline/phase4_state.py
python pipeline/evaluate_pipeline.py        # optional: scores everything against ground truth
python pipeline/evaluate_states.py          # optional: state-by-state TP/FP/TN/FN (below)
```

**Phase 1, events and states (one timeline).** `events/generator.py` simulates every occupant moving on the zone graph and writes three views of that one simulation:
- `generated_events.json`: what a camera sees. Each movement is a capture `{event_id, timestamp, current_building, current_zone, embedding_row}`; it **never** carries `occupant_id` or `home_building`. Uses TEST-split corpus rows only.
- `ground_truth.json`: the same events plus `occupant_id` and `home_building`. Evaluators only.
- `state_truth.json`: the state sequence s_0 … s_n. Transition k says which occupant moved, from where and to where. Replaying it gives the whole-campus truth (who is in which building and zone) after every event. It is written from the same movement records as the events, and `python -m events.validate` checks that the two agree state by state.

Model: every occupant has 20 movements (the corpus has 20 test photos each), 8,000 local plus 2,000 visitor events in total. A movement is a camera event, and between two movements the occupant stays where they are, so their true location is known at every moment. An occupant is off campus until their first event (arrival at their home building's `zT`) and stays at their last location after their last event. Default schedule `spread`: the 20 moves are spread over 08:00–17:00 with at least 30 s between them, so people dwell for minutes to hours. Schedule `burst` (`--schedule burst`) is the original model, with all 20 moves inside one 30–180 s-spaced burst of about 33 minutes. The paper's experiments use `burst` (set explicitly in `paper/run_experiments.py`; its output is byte-identical to the earlier generator). A visitor has `home_building ≠ current_building`.

**Phase 2, local recognition.** For each event, compare the preprocessed embedding with every registered occupant of `current_building`. Accept the best candidate only if ≥ 12 of its 20 references are within 80.43°; ties break on the smallest reference angle. Votes are counts, not probabilities.

**Phase 3, retrieval and verification.** Runs only for local rejections. The current building is excluded from candidates, so a local occupant rejected locally is a *local false negative* and cannot be recovered this way. The shortlist is queried in rank order and stops at the first confirmed match. On a confirmed match at a non-home building's entry zone `zT`, a visit pointer is minted.

**Phase 4, state.** See section 6.

**Reference result** (seed 42, 10 × 50, default `spread` schedule, `python manage.py pipeline` then `python pipeline/evaluate_pipeline.py`): 2,000 visitor events, 1,936 routed after the local check, of which 1,791 are identified correctly (92.5%), 63 wrongly and 82 not recovered; routing recall (right building in the shortlist) 94.5%; 1.47 candidate buildings queried per rejection; overall event accuracy 94.3% (local 95.5%, visitor 89.6%); visit-pointer precision 83.5%. On the original `burst` stream the same measure was 1,778 of 1,935 (91.89%); the numbers differ because the two schedules draw different event streams (other test photos, destinations and event order) from the same seed; the recognition and routing rules are identical. A full pipeline run takes about a minute.

**State-by-state evaluation** (`pipeline/evaluate_states.py`, `python manage.py states`). State s_k is the campus after event k, for k = 0 … n (10,000 states).
- *Ground truth of s_k:* `events/output/state_truth.json`, the generator's own state sequence (section above). Occupants not yet on campus are not in the state.
- *System s_k:* for every occupant identified so far, the building of their latest identified event and the most probable zone of their BSTS belief (`dsts/output/phase4_results.json`).
- *Counts per state*, over (occupant, location) pairs with one location per occupant: **TP** predicted at L and truly at L; **FP** predicted at L but truly elsewhere (including people the system places before they have truly arrived); **FN** truly at L but not predicted there (predicted elsewhere, or not identified yet); **TN** all other pairs (A × L − TP − FP − FN). Precision, recall, F1 and accuracy are computed in every state and then averaged over all states.
- Reported at three levels: `location` (building + zone, 90 labels), `building` (10) and `zone` (9). Output: `evaluate_pipeline/output/state_metrics.json` (averages) and `state_metrics.csv` (one row per state and level).
- `python pipeline/evaluate_states.py --dump-state 3000` prints who truly is in each zone at s_3000 and who the system puts there, with the missed (FN) and wrong (FP) occupants.
- Seed 42, `spread` schedule, averaged over all states. Building + zone: precision 0.94, recall 0.94, F1 0.94 (mean TP 447, FP 29, FN 29). Building only: precision 0.98, recall 0.98. Zone only: 0.95 / 0.95. Accuracy is about 0.999 but is dominated by TN, so read precision, recall and F1.
- Limit: only the identified occupant's belief is read per event; other present visitors that Phase 4 also updates in the database are not read.

**Centralised baseline.** `centralized/` is a hypothetical server holding all galleries, using the same preprocessing and vote rule but no LSH/Bloom. It gives the accuracy ceiling that routing is compared against.

## 5. Routing and recognition details

**Federation contract** (`shared/params.json`): seed 42, LSH code length K = 11, L = 122 code slots, embedding dim 512, Bloom target FPR 0.01 sized for 50 occupants, 20 references per occupant, and a hash over all of it (`params_hash`) that every artifact must carry. `routing_params.json` pins the query-time values: accept angle 80.43°, min votes 12, shortlist 5, 3 probes.

**Enrollment** (`buildinglib/enroll.py`): preprocess (center on the mean face, L2-normalise) → per-occupant centroid → LSH codes → insert `slot × 2048 + code` items into a Bloom filter. Only packed bits and scalars are published (about 10 KB per building): no ids, embeddings or centroids.

**Routing** (`buildinglib/route.py`): the capture is hashed in all L slots; weak bits (smallest margin to the hyperplane) are flipped to make extra probes; each probe is tested against each peer filter; a building's score is the number of distinct matched slots. A score of 40 means 40 slots matched, not 40% or a probability.

**Verification** (`buildinglib/verify.py`): angle to each of an occupant's 20 references; the occupant is accepted if ≥ 12 are inside the threshold.

**Visitor pool** (`buildinglib/node.py`): a person identified once as a visitor is cached (private copy of their references) so repeat captures match locally. Entries expire 4 hours after last seen, are overwritten with zeros on eviction, and the pool wipes an entry that it replaces.

**Failures are visible.** If a sealed exchange fails, that candidate contributes nothing (fail closed) and the reason is recorded in `Identification.failures`, `RetrievalRuntime.secure_failures`, the handler's `exchange_failures` counter and the log. The Phase 3 command prints a warning.

## 6. State, zones and visit pointers

**Zones.** Each building is one flat floor: `z1` Entrance, `z2` Mail room, `z3` Office, `z4` Lounge, `z5` Conference, `z6` Classroom, `z7` Cafeteria (only via exit), `z8` Exit, plus `zT`, the transition zone to the outdoors. Movement between buildings must leave and enter through `zT`. Adjacency lives in `dsts/legacy_state/zones.py`.

**Definition 3.3.** For one event with candidate distances D: σ = population std of D, and p_i = exp(−d_i² / 2σ²) / Σ exp(−d_l² / 2σ²). If all distances are equal, σ = 0 and the result is uniform over the ties. The Bloom score never enters this.

**BSTS.** `StateTable` keeps each occupant's probability over the 9 zones and updates it from the event's evidence. Each persisted event writes 9 rows (one per zone) summing to 1.

**Where it is stored.** Always in the building that *observed* the event: `registered.db` for its own occupants, `visitor.db` for visitors. A full run writes about 90–100 thousand rows in under 30 seconds (WAL mode). Locally accepted events persist only the identified person; a visitor already present is re-matched against every present visitor's cached references and all of them are updated.

**Presence.** A visitor stays present until their own event at `zT` (departure). Entries also expire after the 4-hour TTL; expiry closes their pointer. Expiry assumes events arrive in time order within one day (events carry only a time of day). Pointer-closing errors are logged, not swallowed.

**Visit pointers.** When a building confirms a visitor at its `zT` entry, it sends the person's home building a tiny record (occupant id, current building, timestamps, no biometrics) stored in `pointers.db`. Location queries follow the pointer instead of scanning all 10 buildings. Departure at `zT` closes it.

## 7. Security

The security layer is in `security/` and `nodelib/security_handler.py`. It protects the two things that actually cross a building boundary — the captured embedding and the matched person's reference vectors — and the access paths to tracking data.

| Mechanism | What it does | Where |
|---|---|---|
| Sealed payloads | Per message: ephemeral X25519 → HKDF-SHA256 → AES-128-GCM with the whole header as associated data; Ed25519 signature over header, nonce and ciphertext; `in_reply_to` binds each reply to its request | `security/payload.py` |
| Fail closed | Any failed step (certificate, signature, replay, decrypt, binding) → no reply, nothing admitted | `nodelib/security_handler.py` |
| Certificates | Campus CA issues node certificates; expiry, revocation, subject and pinning are checked; an mTLS session is required per building pair | `security/transport.py` |
| Replay guard | 300 s window plus unique nonces, run **after** signature verification so the timestamp is authenticated | `security/replay_guard.py` |
| Compact framing | Binary arrays (no JSON/base64 inside the ciphertext), base64 envelope fields. Request 3.2 KB, reply 56 KB (about 1.35× raw, was 2.7×). Decoding is strict (type, rank, size, exact length, magic, no trailing bytes) | `nodelib/transfer_codec.py` |
| Visitor pool hygiene | Private copy, 4 h TTL, zeroed on eviction/replacement | `buildinglib/node.py` |
| Signed tokens | HMAC-SHA256, 1 h expiry, mintable only by the server; raw occupant IDs are not tokens | `security/tokens.py` |
| Audit log | Every authorization decision is recorded; bounded deque | `security/authorize.py` |
| Metrics | `/metrics` needs `DSTS_METRICS_TOKEN` or a loopback client | `server.py` |

Secure mode is the default in both `nodelib.deploy.identify` and `RetrievalRuntime`. On the real data it gives the same confirmations as plain mode (checked on a 40-event sample), roughly 4× slower on that sample.

## 8. Access control (RBAC)

**Roles.** 500 occupants = 10 Deans + 100 Teachers + 390 Students (1 Dean, 10 Teachers, 39 Students per building; each teacher has a roster of about 4 students). Assignment is deterministic (seed 42, `build_campus_roles.py`) and saved to `variants/rbac10/`.

**Two layers, both before execution:**

1. **Layer 1 — infrastructure** (`security/authorize.py`): principals are `ADMIN`, `BUILDING_NODE`, `QUERY_CLIENT`. Decides whether a principal may perform an action on a resource and records the decision.
2. **Layer 2 — campus persona policy** (`security/campus_policy.py`): building-scoped hierarchy **Dean (A) > Teacher (B) > Student (C)**. A requester's authority is bounded by their own home building. A *visitor* of building b is someone whose current building is b and whose registered building is not b.

**Disclosure levels** (minimum necessary disclosure):

| Level | Meaning | Example answer to "Where is X?" |
|---|---|---|
| L0 | Refused | — |
| L1 | Presence only | "Available" / "Away" |
| L2 | Building + sector + hour-rounded time + banded confidence | `building_5`, Work & Study Wing, ~10:00, High |
| L3 | Precise current (capped under minimum necessary) | — |
| L4 | Full track: exact zone, time, probability | `z3`, 10:42:17, p = 0.950 |

**Rules in practice:** a Dean sees local occupants at L2 and may reach L4 only in an authorised investigation; visitors in their building are visible while present, their movements outside it are redacted. Teachers see students and peers at L2 (office-hours rules apply). Students are denied access to other people. Trajectory queries (Q3, Q4, Q5, Q7, TRACK) require L4 or are refused. Every decision returns `policy_rule`, `reason`, `visitor_status`, `exposed_fields` and `redacted_fields`; add `--explain` to the CLI to see them. Databases are unchanged: RBAC is a filter between storage and client.

**Enforcement order in the API:** signed token → body `caller_id` must match the token (403 otherwise) → input validation → privileges derived from the role, never from the request → Layer 1 → Layer 2 → engine (cached **behind** the decision) → per-row disclosure filtering for aggregate and zone queries. Dean-only endpoints: reset, simulate, demo-walk, cache-stats. All roles are confined to their own building for aggregates and zone queries.

## 9. Queries

| ID | Question |
|---|---|
| Q1 | Did anyone stay in building b after time t? |
| Q2 | Were more visitors than registered occupants present in b at t? (present = last sighting at or before t is in b and is not a zT departure) |
| Q3 | Did occupant o leave b before t? |
| Q4 | Did o enter between t1 and t2? |
| Q5 | Did o visit all zones of b? |
| Q6 | Where was o at time t? (follows a live visit pointer if one is open) |
| Q7 | How many distinct zones did o visit in [t1, t2]? |
| Q10–Q13 | Zone-level occupancy/visitor lists (per-occupant filtering at L3+, otherwise counts) |
| TRACK | Full trajectory, merged with closed pointer history |

CLI: `python manage.py query --caller <id> --target <id> --query Q6 [--explain]`. The engine runs over `dsts/output/phase4_results.json` and `nodes/*/building.json`. Building (Q1, Q2) and zone (Q10, Q12, Q13) queries follow the same rules on the CLI as in the API: own building only, no zone queries for students, occupant IDs only for a Dean on `security_investigation`/`audit`, counts for everyone else.

### Explanations

Every answer comes with the reasoning behind it (`pipeline/explain.py`). Each query builds its explanation from the same events it answered from: the rule it applied, the evidence with its role (`decisive`, `last_before_t`, `carry_in_state`, `zone_visit`, ...), what it looked for and did not find (`absence`), and uncertainty flags. The flags come from the identification provenance that Phase 4 now stores on every identified row (`provenance`: votes, routing rank, Bloom margin, whether the vote winner was also the nearest candidate). `identity_probability` is not used, because it is close to 1.0 for most misidentifications too.

| Flag | Raised when |
|---|---|
| `vote_winner_not_nearest` | the accepted occupant was not also the nearest candidate (strongest error signal) |
| `low_votes` | fewer than 16 votes (the threshold is 12) |
| `verified_by_lower_ranked_building` | the confirming building was not first on the shortlist |
| `narrow_routing_margin` | the Bloom score gap between the top two buildings is below 5 |
| `stale_observation` | a point-in-time answer rests on a sighting more than 60 minutes old |
| `pointer_based` | a value comes from a visit pointer with no identified sighting behind it: Q6's pointer fast path, or a TRACK pointer segment with no sighting inside it (raised on that segment, not on the whole TRACK answer) |

Explanations are redacted to the caller's disclosure level before they leave the engine (`redact()`), so they never show more than the answer: nothing at L0, only an availability sentence at L1, the current position with sector and hour-rounded time and no routing details at L2, exact zone without history at L3, everything at L4 (minus a visitor's history outside the Dean's building). Aggregates and zone queries show per-person evidence only to an investigating Dean; others get counts. `withheld` lists what was removed and why. `--explain` on the CLI prints the access decision and then the reasoning; `POST /api/query` returns it as `explanation`; the dashboard shows it under the answer.

```
$ python manage.py query --caller 0000362 --target 0000102 --query Q6 --purpose academic_roster --at-time 12:00:00 --explain
  ...
  Disclosed (L2_CURRENT_ZONE): {'building': 'building_7', 'sector': 'Circulation & Access Hub', 'approx_time': '11:00:00', 'confidence': 'High (p>=0.8)'}
  Reasoning (L2_CURRENT_ZONE):
    Rule:        location at t is the last identified sighting at or before t
    Evidence:    1 item(s)
      - [last_before_t] 11:00:00 building_7 Circulation & Access Hub -- present_visitor_pool
    Uncertainty: none
    Withheld:    event IDs; exact times: rounded to the hour; exact zone: functional sector only; identification details (votes, shortlist, verifying building, margins): the routing ones reveal the home building
```

`python paper/explain_overhead.py` measures the cost (`reports/explanation_overhead.json`) and how well the flags catch wrong identifications and wrong answers against ground truth (`reports/explanation_flags.json`: flag precision and recall overall, per query type, per flag, and per pointer segment).

## 10. The website and API

Start it: `DSTS_DEMO_MODE=1 python manage.py serve`, then open http://127.0.0.1:8000.  
> **Prerequisite for clean clones:** Ensure `python manage.py pipeline` has been executed first so that `dsts/output/phase4_results.json`, `events/output/generated_events.json`, and `variants/rbac10/*.json` exist to populate campus state and registries.

**How it works.** `dsts/api/server.py` (FastAPI) serves the static dashboard (`static/index.html`, `app.js`, `style.css`) and a JSON API. At boot the page asks `POST /api/auth/login` for tokens for the three personas (Dean `0001738`, Teacher `0000362`, Student `0000168`, all building_5); with demo mode off the page shows the server's 403 message. Every request sends the active persona's bearer token; on a 401 the page re-signs in. The persona switcher swaps tokens and refetches everything. A WebSocket (`/ws/live?token=`) streams live events.

## 11. Experimental setup and the paper

`paper/` holds everything that produced the paper's numbers.

```
paper/run_experiments.py    the experiments (modes: clean, rpsmall, scale, member, openset); paths are relative to the repo
paper/analytic_costs.py     tau and analytic costs from the reference photos
paper/build_paper.py        fills paper_template.txt from results/*.json and writes paper.tex
paper/paper.tex             the Springer LNCS paper (generated; do not hand-edit numbers)
paper/results/*.json        stored outputs of every experiment
paper/tools/                check_tex.py, check_springer.py, estimate_pages.py
paper/reproduce.sh          runs all of the above in order
```

**Setup.** 500 enrolled people in 10 buildings of 50, 20 reference photos each; the rest are test photos. 20 seeds. Each seed re-partitions the same 500 people into different groups of 50 and redraws the LSH hyperplanes, the Bloom salt and the event stream. Reported values are means with 95% Student-t confidence intervals (19 degrees of freedom), plus paired differences.

**Clean protocol.** The mean face and the accept angle τ come from reference photos only (`DSTS_MEAN_FROM=refs`); test photos never influence parameters. τ = 80.43° (stored unrounded as 80.43167; `reproduce.sh` passes the unrounded value through `DSTS_TAU`), V = 12 of 20 votes, shortlist S = 5, K = 11 (L = 122) with 3 probes unless a table says otherwise.

**What each mode produces:** `clean` main results (probe sweep, K/L, adaptive shortlisting policies, central baseline); `rpsmall` B = 2 and B = 5 building scopes; `scale` scaling with building count; `member` membership-leakage measurement of the published filters; `openset` unknown-person (visitor) behaviour at several V. The paper focuses on **enrolled people** routing; unknown-visitor identification is future work.

**Scope of the claims.** The paper evaluates routing accuracy and cost. The sealed channel described in section 7 is implemented and unit-tested but is **not part of the reported experiments and its cost is not measured there** (the repository measurement above is a code-level figure). The 20 seeds vary the grouping of the same 500 people and the hash randomness; they do not add new people or photos.

**Reproduce.** `bash paper/reproduce.sh` (about 10–30 minutes). Checked in this repository: the 20-seed `clean` run reproduces `dacs_clean_runs.json` byte for byte (about 17–27 minutes); the `rpsmall`, `scale`, `member` and `openset` modes were not re-run after the move; `build_paper.py` regenerates `paper.tex` byte-for-byte from the stored results, and `analytic_costs.py` regenerates `clean_analytic.json` identically. `python paper/tools/check_tex.py paper/paper.tex` checks braces and references. No LaTeX compiler is installed in the dev environment; compile in Overleaf or a local TeX install.

## 14. Decision log

**First review of the test_6 branch** found: no authentication (caller id from the body), self-asserted privileges, open endpoints returning every occupant, Q1/Q2 skipping Layer 2, default Grafana credentials, and a response cache in front of authorization. All were fixed in the passes below.

**Pass 2, RBAC.** Tokens are signed, stateless and expire in 1 h (no session store: there are no user accounts, a JWT dependency was not worth about 40 lines). Secret from `DSTS_TOKEN_SECRET`, random otherwise. Two explicit login paths (demo personas behind `DSTS_DEMO_MODE`, or id + `DSTS_LOGIN_KEY` compared with `hmac.compare_digest`). Authorization always runs first and is audited; only the engine computation is cached, keyed by everything the decision depends on. Zone queries filter per occupant at L3+ rather than blanket-deny, which reuses one source of truth. Deans are confined to their own building; a campus-wide view needs a separate admin role. Admin and simulation endpoints are Dean-only; reset never clears the audit log. `/metrics` uses a static bearer token (what Prometheus supports) or loopback. Health stays public but minimal.

**Pass 3, sealed transfer.** The encrypted envelope had carried only placeholder metadata while the capture and 20×512 reference tensor moved in plaintext, and the batch pipeline had no security at all. Fixed with sealed payloads, request/reply binding, replay check after signature, sender key from the CA certificate, fail-closed behaviour (no silent plaintext fallback), the same sealed path in the batch pipeline, and a visitor pool with a private copy, TTL and wiping.

**Pass 4, browser verification.** Driving the real dashboard as Dean, Teacher and Student found and fixed: `/api/occupancy` bypassing the persona policy, a role-dependent response shape, totals derived from filtered rows, an events counter stuck at 0, a security log with wrong fields and start-up noise, stale data after persona switch, and Dean-only buttons clickable by other personas.

**Pass 5, review fixes.** Replaced visitors are wiped; exchange failures are recorded and logged; Phase 4 expiry catches only I/O and database errors; wire size roughly halved; audit log bounded; unused imports and a dead re-export block removed; undefined `Optional` fixed; `manage.py` and this single document added; paper experiments moved into the repo with relative paths.

## 15. Known limits and residual risks

**System**
- In-process simulation: arrays are plaintext in Python memory before sealing and after opening. No real network, camera or face detector.
- X25519 public keys are not certified (the CA certificate binds only the Ed25519 key).
- Phase 4 re-reads a visitor's references from the corpus rather than from the sealed reply.
- Wiping is best-effort; Python cannot guarantee no other copy of an array remains.
- The 4 h TTL is a fixed default.
- Only the synthetic 500-person, 10-building corpus is measured; larger scale is untested.
- Phase 3 cannot recover a local occupant rejected locally (current building is excluded by design).

**Web/API**
- The WebSocket token is in the query string (browsers cannot set headers on upgrades); the 1 h expiry limits the exposure.
- One shared `DSTS_LOGIN_KEY` unlocks any occupant; no rate limiting. No TLS unless a reverse proxy adds it.
- `is_office_hours`: In replay mode (default), derived from the query/event timestamp (`at_time`) so historical benchmark queries reflect policy as of that moment. For live policy enforcement, setting `DSTS_LIVE_POLICY=1` enforces real-time wall-clock office hours (`datetime.now()`).
- Token secret (when random), caches and the simulated event list are per process.
- In demo mode any dashboard viewer can act as any of the three personas, by design.

**Git hygiene.** Source, tests, contracts and small config are tracked. Generated outputs (`*/output/`, corpus, `variants/`, per-node embeddings) are git-ignored and regenerable. Running Phase 4 modifies the tracked empty `nodes/*/state/*.db` files; reset or ignore them as you prefer.
